# Product Guidelines

## Product Requirement Principles

Product requirements should clearly explain:

- Who needs the capability
- What the user needs to do
- Why the capability provides value
- What behavior is expected
- How alternative or exceptional situations should behave

## Requirement Quality

Requirements should be:

- Clear
- Specific
- Testable
- User-focused
- Business-oriented
- Free from unnecessary implementation assumptions

## Scope Management

The product requirement should represent the requested capability.

Do not automatically add:

- Additional features
- Marketing functionality
- Social sharing
- Analytics
- Notifications
- Integrations
- Administrative functionality

unless these are explicitly requested or are essential to the described user outcome.

## Acceptance Criteria

Acceptance criteria should describe observable functional behavior.

Avoid implementation-specific criteria.

## Edge Cases

Edge cases should be relevant to the requested feature.

Good edge cases include:

- Invalid values
- Missing values
- Expired information
- Duplicate actions
- Unauthorized actions
- Interrupted operations
- Boundary conditions

## Priority Assessment

Priority should reflect:

### High

Use when the requirement has significant user/business impact, is urgent, or addresses a critical user problem.

### Medium

Use when the requirement provides meaningful value but is not immediately critical.

### Low

Use when the requirement provides useful but relatively lower-impact functionality.

Priority justification should explain the reasoning rather than simply state the priority.
